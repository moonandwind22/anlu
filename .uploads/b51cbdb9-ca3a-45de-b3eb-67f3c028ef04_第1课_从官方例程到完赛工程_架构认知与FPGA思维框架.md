## 官方例程架构拆解

现在你已经跑通了例程，我们搞清楚：**这个系统到底是怎么工作的？**

### 3.1 顶层模块总览

**顶层文件**：`top_tf_hdmi_audio.v`
**模块名**：`top`（注意：文件名和模块名不一致，官方历史遗留问题）

#### 顶层关键参数

```verilog
parameter FRAME_PIXELS = 24'd307200;  // 640×480 = 307200像素
parameter BUF0_ADDR    = 24'd0;        // 帧缓存0起始地址
parameter BUF1_ADDR    = FRAME_PIXELS; // 帧缓存1起始地址（双缓冲）
```

> **理解即可**：SDRAM里划了两块帧缓存，每块307200个32位字。一块显示，另一块加载下一张图，加载完再切换——这就是双缓冲，是视频系统最核心的设计之一。

### 3.2 三大时钟域（理解整个系统的关键）

官方例程用了 **3个PLL，产生4个时钟频率**，分布在3个时钟域：

| PLL | 输出时钟 | 频率 | 时钟域 | 驱动哪些模块 |
|---|---|---|---|---|
| sys_pll | sd_card_clk | 100MHz | TF卡域 | `sd_card_bmp`内部逻辑、SD卡SPI |
| sys_pll | ext_mem_clk | 100MHz | SDRAM域 | `sdram`控制器、`frame_read_write`写侧 |
| sys_pll | ext_mem_clk_sft | 100MHz（相移） | SDRAM域 | SDRAM数据采样（相位偏移保证建立时间） |
| video_pll | video_clk | 25MHz | 视频域 | 视频时序、`frame_read_write`读侧、HDMI像素时钟 |
| video_pll | hdmi_5x_clk | 125MHz | 视频域 | HDMI TMDS串行化（5倍像素时钟） |
| PLL_HDMI_AUDIO | audio_mclk | 12.288MHz | 音频域 | 音频测试音、I2S接口 |

> **设计思维**：为什么需要这么多时钟？
> - TF卡读取要快（100MHz），视频显示要标准（25MHz=640×480@60Hz），两者速率不同 → 需要跨时钟域处理
> - SDRAM需要相位偏移时钟来采样数据，保证建立时间满足
> - HDMI串行化需要5倍像素时钟（DDR模式下）
> - 音频需要标准的12.288MHz（48kHz×256）
>
> **核心原则**：时钟是FPGA设计的生命线。后续修改代码时，**绝对不要乱动PLL配置和时钟频率**，只在各自时钟域内修改逻辑。

### 3.3 核心数据流向（一图看懂整个系统）

```
┌─────────────────────────────────────────────────────────────┐
│                    TF卡域 (sd_card_clk 100MHz)               │
│  TF卡 → sd_card_top → SPI协议 → 扇区数据                     │
│         → bmp_read → BMP解析 → 24位RGB像素                  │
│         → frame_fifo_write → 异步FIFO（跨时钟域）            │
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│                  SDRAM域 (ext_mem_clk 100MHz)                │
│  frame_read_write 写侧 → SDRAM双缓冲（BUF0/BUF1）           │
│         → SDRAM控制器（加密IP）                               │
│         → frame_read_write 读侧 → 异步FIFO                   │
└──────────────────────────┬──────────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────────┐
│                   视频域 (video_clk 25MHz)                   │
│  video_timing_data → 640×480@60Hz时序（HS/VS/DE）          │
│         → video_delay → 时序对齐延迟                          │
│         → video_rgb_to_axis → 转AXIS视频流                   │
│         → hdmi_1_4b_transmitter_core（加密IP）→ TMDS编码    │
│         → hdmi_phy_wrapper → ODDR串行化 → HDMI输出           │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                   音频域 (audio_mclk 12.288MHz)              │
│  hdmi_audio_tone_i2s_64fs → 1kHz测试音 + I2S接口            │
│         → I2S_receiver → 左右声道PCM数据                     │
│         → audio_arc_calculate → 音频时钟恢复（ACR）          │
│         → 送入HDMI核心，和视频一起打包输出                     │
└─────────────────────────────────────────────────────────────┘
```

## 四、第三部分：官方例程的设计思维（为什么这么设计）

看懂了"是什么"，我们再深入一层：**官方工程师为什么要这么设计？遇到一个需求，从哪些角度思考？**

### 4.1 为什么要分层？

官方例程清晰地分成了四层：
- **驱动层**：SPI、SDRAM、HDMI（最底层，直接和硬件打交道）
- **协议层**：SD卡命令、BMP解析、HDMI TMDS（协议解析）
- **缓存层**：FIFO、SDRAM双缓冲（数据缓存和速率匹配）
- **应用层**：图片切换、自动轮播、状态控制（业务逻辑）

> **设计思维**：分层的核心目的是**隔离变化**。
> - 底层驱动是稳定的（SDRAM控制器、HDMI发射器一旦调好就不用动）
> - 应用层是经常变的（切换逻辑、轮播速度、显示内容）
> - 分层之后，改应用层不会影响底层，改底层也不会破坏应用层
>
> **反面教材**：如果把所有逻辑写在一个文件里，改一个按键消抖可能不小心改坏了HDMI时序，排查起来非常痛苦。

### 4.2 为什么需要多个时钟域？

前面讲了3个时钟域、4个时钟频率。为什么不能用一个时钟搞定一切？

> **设计思维**：时钟域划分的核心原则是**"按速率和标准分组"**。
> - 视频显示有严格的标准（640×480@60Hz = 25MHz像素时钟），不能随便改
> - TF卡读取越快越好（100MHz），但和视频速率不匹配
> - 音频有自己的标准时钟（12.288MHz = 48kHz×256）
> - 不同速率的模块之间用异步FIFO做跨时钟域处理
>
> **思考问题**：如果强行用25MHz读TF卡，会发生什么？
> → 读取速度太慢，一帧图片还没读完，显示端已经开始读下一帧了，导致花屏。这就是为什么需要更快的时钟读TF卡。

### 4.3 为什么要用双缓冲？

单缓冲的问题：读和写同时访问同一块内存，会导致"写了一半就读出来"，画面上半部分是新图、下半部分是旧图——这就是**撕裂**。

双缓冲的解决：
- 一块缓冲区正在显示（读）
- 另一块缓冲区在后台加载新图（写）
- 新图整帧加载完成后，**瞬间切换**显示指针到新缓冲区
- 切换只需要改一个地址寄存器，一个时钟周期完成，观众看不到过程

> **设计思维**：双缓冲的核心是**"原子提交"**——要么显示完整的旧图，要么显示完整的新图，永远不会显示"半新半旧"的中间状态。
>
> **延伸思考**：这个思想在很多地方都有用——数据库事务、GUI双缓冲、网络数据包重组，本质都是"先在后台准备好，准备完了一次性切换"。

### 4.4 为什么要跨时钟域同步？

`sd_card_bmp`在100MHz时钟域，`frame_read_write`的写侧也在100MHz，但SDRAM控制器在`ext_mem_clk`（也是100MHz但不同PLL输出），读侧在25MHz视频域。不同时钟域之间直接传信号会有**亚稳态**风险。

官方的做法：
- 用 `write_finish_toggle`（电平翻转）代替单拍脉冲
- 接收端用三级寄存器同步（`wrfin_tgl_sync[2:0]`）
- 用相邻两位的异或检测脉冲（`wrfin_tgl_sync[2] ^ wrfin_tgl_sync[1]`）

> **设计思维**：跨时钟域同步的核心原则是**"用电平代替脉冲，用多级寄存器打拍"**。
> - 单拍脉冲在跨时钟域时可能被采样不到（太快了）
> - 电平翻转会保持至少一个时钟周期，更容易被采样到
> - 多级寄存器打拍可以降低亚稳态传播的概率
>
> **这是FPGA设计中最容易出问题的地方之一**，后面调试花屏时，跨时钟域是重点排查方向。

### 4.5 遇到一个需求，从哪些角度思考方案？

总结官方例程的设计思路，遇到一个新需求（比如"加上一张功能"），应该从这几个角度思考：

| 思考维度 | 问自己什么问题 | 官方例程的体现 |
|---|---|---|
| **功能边界** | 这个需求改哪一层？影响哪些模块？ | 加上一张只改`sd_card_bmp`的状态机，不碰底层 |
| **时钟域** | 这个逻辑在哪个时钟域？需要跨域吗？ | 按键消抖在sd_card_clk域，和状态机同域，不需要跨域 |
| **资源占用** | 需要多少LUT/REG/BRAM？够用吗？ | 加一个上一张只需要加几行代码，资源几乎不增加 |
| **时序收敛** | 会不会影响关键路径？setup/hold能满足吗？ | 只改应用层状态机，不影响HDMI高速路径 |
| **稳定性** | 异常情况怎么办？忙的时候按按键会怎样？ | 用`next_req_pending`挂起请求，忙时只记1次 |
| **可扩展性** | 以后再加功能会不会很麻烦？ | 参数化设计，改图片数量只改一个parameter |

> **这就是设计思维的核心框架**。后面每一课讲具体修改时，都会用这个框架来分析"为什么这么改、有没有更好的方案"。

## 五、第四部分：完赛工程总览：从官方到国一的跨越（15分钟）

### 5.1 完赛工程整体架构

完赛工程 `2026_topic1_media_player_zhipu_excellence_promax` 不是在官方例程上"加了几个模块"，而是**从架构层面完全重写**的国一级项目。

它的RTL代码分成了14个功能模块：

| 模块分类 | 包含的核心模块 | 功能 | 和官方的区别 |
|---|---|---|---|
| **storage** | `sd_media_service`、`sd_spi_*`（5个模块） | SD卡SPI协议栈，五层结构 | 官方是单模块`sd_card_top`，完赛是完整协议栈 |
| **filesystem** | `fat32_file_streamer`、`fat32_volume_scanner` | 完整FAT32只读文件系统 | 官方是直接扇区扫描，完赛支持文件名、目录、FAT链 |
| **image** | `bmp24_decoder` | BMP24解码器，分阶段头校验 | 官方是`bmp_read`，完赛有更严格的校验和错误处理 |
| **memory** | `media_frame_loader`、`media_frame_reader`、`media_sdram_write_cdc` | 四bank帧缓存，loader/reader分离 | 官方是双缓冲，完赛是四bank，支持更多图片和转场 |
| **control** | `media_player_control`、`media_policy`、`fast_boot_gate` | 播放器控制状态机、策略、快速启动 | 官方是`sd_card_bmp`里的简易状态机 |
| **display** | `osd_overlay_24`、`video_fade_transition`、`frame_blend`、`promax_audio_waveform`等（9个模块） | OSD叠加、转场特效、图层混合、音频波形 | 官方完全没有这些扩展功能 |
| **audio** | `audio_source_mux`、`wav_stream_player`、`pcm_test_tone`、`sync_fade_gain`等（7个模块） | 音频源多路选择、WAV播放、淡入淡出 | 官方只有1kHz测试音 |
| **io** | `seg7_panel`、`param_menu_controller`、`dual_key_chord_router`、`uart_status_reporter`等（10个模块） | 数码管、参数菜单、双键组合、UART状态报告 | 官方只有简易数码管和两个按键 |

| **recovery** | `media_recovery_fsm` | 媒体恢复状态机，有界重试，错误跳过 | 官方完全没有，出错就卡死 |

| **integration** | `media_video_pipeline`、`media_ingest_pipeline`等（5个模块） | 流水线集成，把各模块串起来 | 官方是顶层直接连线 |

### 5.2 和官方例程的5个本质区别

| 维度 | 官方例程 | 完赛工程ProMax | 为什么要改 |
|---|---|---|---|
| **文件系统** | 直接扇区扫描，按拷贝顺序识别图片 | 完整FAT32文件系统，支持文件名、目录、FAT链 | 官方换图要按顺序拷贝，非常麻烦；完赛直接按文件名读取 |
| **帧缓存架构** | 双缓冲（2块BUF） | 四bank帧缓存（loader/reader分离） | 双缓冲只能支持简单切换；四bank支持转场特效、多图预加载 |
| **错误处理** | 无，坏图/卡异常会卡死 | 完整恢复FSM，有界重试，坏图跳过，sticky错误账本 | 竞赛现场什么TF卡都有，必须能容错 |
| **配置持久化** | 无，断电设置丢失 | Flash安全写，双记录CRC，版本管理 | 音量、亮度、轮播周期等设置需要保存 |
| **可观测性** | 只有数码管状态码 | UART状态报告、性能探针、SDRAM BIST、错误码OSD | 调试效率提升10倍，出问题不用猜 |

### 5.3 为什么要从官方过渡到完赛？（官方的5大致命局限）

官方例程能跑，但要拿奖、要稳定演示，有5个致命问题：

1. **换图极其麻烦**：必须按扇区顺序拷贝，文件名没用，换一张图要重新格式化整个卡
2. **没有容错**：遇到坏图、劣质TF卡，状态机直接卡死，只能重启——竞赛现场这是灾难
3. **扩展功能加不上去**：双缓冲架构想加转场特效、OSD叠加，会发现缓存不够用、架构不支持
4. **调试全靠猜**：没有UART日志、没有性能探针，出了问题只能看屏幕猜
5. **设置不能保存**：音量、亮度调好，断电就没了

> 六、第五部分：FPGA视频系统的三大思维框架（20分钟，核心）

这是本课最重要的部分。**代码会忘，但思维方式会一直跟着你。**

### 设计思维：遇到需求，从哪些角度思考方案？

前面4.5节已经给了一个6维框架，这里再总结成更通用的**"设计四问"**：

#### 第一问：改哪一层？

- 这个需求是驱动层、协议层、缓存层还是应用层？
- 能不能只改应用层，不动底层？
- 如果必须动底层，会不会影响其他模块？

> **案例**：加上一张功能——只改`sd_card_bmp`的状态机（应用层），完全不碰SDRAM、HDMI等底层。这就是好的设计。

#### 第二问：在哪个时钟域？
- 这个逻辑在哪个时钟域运行？
- 输入信号来自哪个时钟域？需要跨域同步吗？
- 输出信号到哪个时钟域？会有时序问题吗？

> **案例**：按键消抖在sd_card_clk（100MHz）域，和图片切换状态机同域，不需要跨域。但如果要把按键状态传到视频域做OSD显示，就需要跨域同步。

#### 第三问：异常情况怎么办？
- 正常流程是什么？
- 异常情况有哪些？（忙的时候按按键、卡拔了、图片坏了、SDRAM超时）
- 每种异常怎么处理？是重试、跳过、还是报错？

> **案例**：官方的`next_req_pending`就是处理"加载忙的时候按按键"的异常——不立即执行，而是挂起请求，等当前加载完再执行。这就是防御式编程。

#### 第四问：怎么验证是对的？
- 正常情况怎么验证？
- 边界情况怎么验证？（图片数量0/1/4、连续快速按按键、长时间运行）
- 异常情况怎么验证？（拔卡、坏图、断电重启）

> **这是最容易被忽略的一问**。很多人改完代码，编译通过、上板能跑，就觉得"好了"。但没有经过边界和异常测试的代码，竞赛现场一定会出问题。

### 6.2 调试思维：出现问题，从哪些方向排查？

这是最实用的部分。FPGA视频系统最常见的问题就是**花屏、黑屏、撕裂、卡顿**。出现这些问题时，从哪些方向排查？

#### 第一步：先分类——这是什么类型的问题？

| 现象 | 可能的问题层级 |
|---|---|
| **完全黑屏/无信号** | HDMI物理层、时钟、PLL、引脚 |
| **有信号但全黑/纯色** | 视频时序、DE信号、像素数据全0 |
| **花屏/竖条/颜色不对** | 像素数据错误、FIFO、SDRAM、BMP解析 |
| **画面撕裂（半新半旧）** | 双缓冲切换时机不对、没有在场消隐期切换 |
| **周期性卡顿/闪烁** | 带宽不足、FIFO欠载、SDRAM刷新冲突 |
| **运行一段时间后死机** | 时序违例、复位问题、内存泄漏、状态机死锁 |

#### 第二步：从外向内，逐层排查（责任层级法）

这是从完赛工程花屏攻坚复盘里总结出来的**最有效的排查方法**：

```
1. 官方HDMI内部TPG（测试图）→ 验证HDMI最后一公里
2. 外部AXIS本地彩条 → 验证AXIS接口和HDMI核心
3. 像素域本地产生图案 → 验证视频时序和像素消费端
4. 跨时钟FIFO合成图案 → 验证FIFO和跨时钟域
5. SDRAM返回节奏 + 合成数据 → 验证SDRAM读控制
6. 真实SDRAM数据 → 验证SDRAM读写
7. TF/FAT/BMP → 验证文件读取和解析
8. OSD/字幕/波形 → 验证叠加层
9. 完整产品循环 → 验证整体稳定性
```

> **核心原则**：每一级只比上一级多一个责任边界。从最外层（HDMI）开始，一层一层往里查，找到第一个出问题的层级，就是根因所在。

#### 第三步：单变量隔离——一次只改一个东西

> **从花屏攻坚复盘里学到的最深刻教训**：
> 不要同时改多个东西然后上板看结果——如果好了，不知道是哪个改对了；如果坏了，不知道是哪个改坏了。
>
> **正确做法**：每轮实验写清四件事：
> - **唯一变量**：这轮只改了什么
> - **保持不变**：哪些层没动
> - **预期A**：如果结果是A，排除什么
> - **预期B**：如果结果是B，排除什么
>
> **案例**：花屏排查时，保持板卡、HDMI、时钟、约束全部不变，唯一变量是"ProMax改造FIFO vs 官方原始FIFO"。结果花屏→清晰，直接锁定FIFO是根因。这就是单变量隔离的威力。

#### 第四步：诊断工具要自证——不要相信"我觉得旁路了"

> **另一个深刻教训**：
> 写了一个诊断模式，说"我绕过SDRAM了"，但实际上原路径的请求还在发、返回还在处理——诊断模式本身有bug，结果当然不可信。
>
> **诊断工具自证清单**：
> - 原生产者的请求是否真的被禁止？
> - 原返回是否真的被忽略？
> - 计数器是否只统计实际握手？
> - 突发长度是否符合vendor合同？
> - 诊断文件是否被正式工程实际引用？
>
> **原则**："设置了DIAG参数"不等于"真的隔离了变量"。必须从端口和状态机逐行证明原路径已被切断。

#### 第五步：证据强度分级——不要把弱证据当结论

| 证据等级 | 证据类型 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 1级（最弱） | 仿真通过 | RTL在模型下自洽 | 真实芯片时序、加密IP行为 |
| 2级 | UART日志/LED状态 | 控制状态机在运行 | 最终像素数据是否正确 |
| 3级 | 单帧实拍 | 这一帧画面是对的 | 长时间稳定性、切换是否正常 |
| 4级 | 完整循环实拍 | 功能完整、切换正常 | 长时间稳定性、异常容错 |
| 5级（最强） | 60分钟长稳+冷启动+多sink | 真正可交付的稳定性 | —— |

> **核心原则**：UART显示"PIC 1切换了"，不代表画面真的对了；仿真全绿，不代表上板能跑。**只有HDMI实拍画面才是最终裁判**。

### 6.3 验证思维：怎么证明一个修改是真的改对了？

改完代码、编译通过、上板能跑，这只是第一步。**怎么证明是真的改对了，而不是"碰巧好了"？**

#### 验证三层次

**第一层：功能验证——正常情况对不对？**
- 核心功能是否正常？（显示、切换、轮播、音频）
- 边界情况是否正常？（1张图、4张图、连续快速切换）
- 参数配置是否生效？（改轮播周期、改音量）

**第二层：稳定性验证——长时间会不会出问题？**
- 连续运行30分钟有没有死机、花屏？
- 自动轮播100轮有没有出错？
- 反复按键有没有连跳、漏跳？

**第三层：容错验证——异常情况会不会崩？**

- 运行中拔TF卡会不会死机？插回去能不能恢复？
- 放一张坏图会不会卡死？还是能跳过？
- 断电重启能不能正常工作？
